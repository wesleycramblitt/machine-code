We need to implement the orchestration feature. You may see references to an old verion of it from before, this one will function differently. It can only be triggered from the repo level. From the runs page, hit "o" to go to the orchestration page for that repository (whatever is selected). If no repo is selected, it isn't available. The page should have the Back[Esc] with a red background at the top left and a page title like many otehr TUI pages.  It should show the orchestration status and have a few settings. status is either Inactive or Running. Settings include: processes (1, 2, 4, 8). tier: local or cloud.  Engineer minFit:  4-8.5 (selection in 0.25 increments)  model preview: [list model name chosen by settings]   research minFit: .... same as engineer...      Start[:!].   Some indication settings: Running: 5  Awaiting: 3  Failed: 2.    If Running, you can stop with Stop[:!].   What does "running" mean?, When started, it looks at how many processes it can use and how many runs are currently running, if any processes are available, it finds the next unblocked issue to run, and starts a new run with the settings (attached to the issue). If an issue finishes and that frees up a process, the next available issue runs.  The order it should (unblocked) bugs, then features, then ideas.   If a run hard fails (not just an acceptance gate where the run continues, a hard failure), the orchestrator will kick off the next available issue.  If a run is awaiting some kind of input, the same will happen, move on to another issue.   This allows the orchestrator to keep moving without human input. If no issues are unblocked and ready, it waits until they free up to start more runs. If stopped at any point, it doesn't kill the runnning runs, it just stops orchestrating. When the orchestrator is running, we should have an indicator like Orchestrating...  to the right of the repo name in the runs page with a purple background so it stands out. If a user goes to the orchestration details page while it is orchestrating, a user can edit the settings and they pick up on the next run (processes, minfit, and so on). Turn this into nicely scoped features that depend on each other appropriately.
